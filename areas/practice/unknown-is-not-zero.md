## 原則

**「分からない」は、それ自体を1つの状態として持つ。**「無い」「0」「前の値のまま」と同じ場所に入れない。

同じ場所に入れると区別できなくなる組は、いつも同じ構図になっている。**片方が「実際にそうだった」、もう片方が「確かめられなかった」。**

| 実際にそうだった | 確かめられなかった |
|---|---|
| 0件だった | 数えられなかった |
| 合図が無かった | 合図が届かなかった |
| その間なにも使っていない | その間を測っていない |
| いまの枠の数字 | もう終わった枠の数字 |
| 止めなくてよい | 止めるべきか確かめられなかった |

## なぜ

**ひとまとめにしてしまうと、壊れたときに何の兆候も出ない。**

同じ「重なってはいけないものが重なった」でも、壊れ方には種類がある。取り合いになれば**暴走**し、
待ち合わせが噛み合わなければ**膠着**する。どちらも誰かが気づく。**この壊れ方だけは、正常に見えたまま、何の兆候もなく間違う。**
「0件」「変化なし」「使っていません」は、どれも**正しい出力として読める**。

だから見つかるのは、たいてい**ずっと後**になる。そして後から遡っても、
**0 が本当の 0 だったのか、測れなかったのかは、もう区別がつかない。**

## どう使う

- **3つ目の値を持つ**。真偽の2つで足りないなら、3つ目に名前を付けて状態として持たせる
  （`None`、`window_unknown`、「数えられませんでした」）
- **その3つ目を、答えと同じ並びに置かない。**「分からない」を持っていても、
  それが答えの選択肢の1つとして並んでいると、**答えを先に飲み込んでしまう。**
  「進めてよい／止める／取り直す」を1つの欄で返すと、取り直すべき間は止める判定が出ない。
  **分からないことは別の欄に出し、本来の判定はその前で行う**

  **持つだけでは足りないことを示す例が、2つある**。1つは上の「答えの並びに混ぜた」。
  もう1つは**読む側**で、別の欄に正しく持っていても、
  **読む側が分岐を書き忘れると、「分からない」が実測と同じに数えられる**
- **書き手自身が消えるなら、消える前に書いておく。**「分からない」を値として持てるのは、
  **持つ側が動いている間だけ**だ。止まった側は、**「書けなかった」と書くこともできない**——
  書けない状態だからだ。だから、**まだ書ける側が先に書く**。
  「ここがこのままなら、次は動けなかったということです」と、残るほうの場所に書いておく
- **先に書くなら、「約束」の形で書く。**「次はいつ来るか」（来ないならその理由）を、書ける側が毎回残す。
  **監視する側は、最後の記録の古さではなく、約束と今を比べる**。古さだけで見ると、
  **静かな正常（やることが無かった）と死（実行されなかった）が必ず同じ見た目になる。**
  動いたが何もしなかったときは行を残せるが、**実行されなかったときは動いていないので何も書けない**——記録が無いことに気づかせる方法は、止まる前に残しておく約束しかない
- **生まれたばかりの仕組みは、自分ではまだ書けない**。自分の生存を自分の記録で示す仕組みは、
  記録を書けるようになる（許可が下りる・設定が済む）までは何も言えない。**そのあいだ「書ける側」は作った側にしかいない。**
  作った時刻を残しておき、**そこから起動するはずだった回数**を数えれば、「まだ一度も起動していない」と「起動したが詰まっている」が分けられる
  （→ [fix-must-not-ride-the-broken-path](fix-must-not-ride-the-broken-path.md)）
- **どちらの型を使うかは、一問で決まる**。**区別できなくなる2つを見ている側は、そのとき動いているか。**
  動いているなら**値を分ける**。消えるなら**先に書く**
- **分からないときは、安全なほうとして扱う**。どちらが安全かは場面で決まるので、
  **どちらとして扱うかと、なぜそちらが安全かを、その扱いを決めている箇所に書く**
- **測れていない期間を 0 で埋めない**。0 で埋めるのは「その間なにも起きなかった」と**主張する**こと。
  分からないことを、何の知らせもなく「起きなかった」に変えている
- **区別できなくなっていないかの見つけ方は1つ。出力が同じになる2つの入力を探す。**
  「本当に 0 だったとき」と「測れなかったとき」の両方を入力して、
  **出力が1文字も違わないなら、そこでは2つが区別できなくなっている**
- **壊して試す**。直したつもりの判定は、わざと壊した状態で動かして、
  0 ではなく「分からない」と出ることを目で見る

## 根拠

### この環境で起きたこと

2026-09-21、一晩で5件出た。**どれも別々のスレッドが別々の経緯で見つけたのに、直し方まで同じだった**
——**区別できなくなっていた2つを別の値として持ち、分からないときは安全なほうとして扱う**。

- **0件と、数えられなかった**。画面から件数を数える仕掛けで、範囲が見つからなくても空の結果が返るため、
  止まっていることを示すラベルが出ているのに件数だけ消えた。**実機（画面を出さずに動かした Chromium）で確認済み。**
  わざと壊した状態でも試し、0件ではなく「数えられませんでした」と出ることを見た
- **合図が無かったと、合図が届かなかった**。待つ側からは同じに見え、止まったままなので誰も気づかない
- **測っていない分が、0 として数えられた**。使用率を引き算の残りで出していたため、
  **クラウドで動いた分が、まるごと作者の使用に化けた**
- **いまの枠の数字と、もう終わった枠の数字**。記録が古くてリセットをまたぐと、
  前の枠の使用率を今の枠のものとして読む。`usage-autopilot/tools/budget.py` は
  `window_unknown` を別に持ち、それが立ったときは守る側の判定にしている
- **動かなかったと、動いた結果なにも変わらなかった**。5時間ごとに書き換わる1枚のページで、
  次の回が枠切れで動けない見込みが立った。**動かなければ何も書かれず、
  書けない状態なので「書けなかった」とも書けない**。そこで、まだ書けるうちに、
  その回のページの末尾へ「**次の回の予定時刻を過ぎてもこのページが「第2回」のままだったら、
  次の回が動けなかった、ということです**」と書いた
  （回の記録 `usage-autopilot/report/rounds/2026-09-22_0210.md`
  「この回自身が動けなかったときに、それが分かる形（先に入れた）」で確認）。
  **その注意書きは、いちばん新しい回の分しかページに載らない**——回が進むと古い行は外れる
  （いまページにあるのは次の回の1本だけで、こちらで数えて1件）。
  つまり**先に書いたことは、書いた場所には残らない。**
  **この型を使うときは、やったことの記録を別の場所に残す**
- **止めなくてよいと、止めるべきか確かめられなかった。帰結がいちばん重い。**
  同じ `budget.py` の止める判定で、「記録が古い」が答えの並びに入っていたため、
  **古いあいだは止める判定がそちらに飲み込まれて出なかった。**
  そして**記録が古くなるのは、たいてい自律実行だけが動いている時間**——
  人が見ていなくて、使用率を取る定期実行が許可待ちで止まっているとき。
  **いちばん止まってほしいときに、気づかれないまま何も起きない**作りだった

**5件とも、同じところへ収束した**——区別できなくなっていた2つを別々に持ち、分からないときは安全なほうとして扱う。
5件目の直しは、**`stale` を消さずに欄として残したまま、止める判定をその前に出す**やり方（`budget.py` の実物で確認）。
**消すのではなく、別に持つ。**

**その `budget.py` は、この考え方を先に言葉にしていた**（`advance()` の説明、原文）。

> **足し戻せないときは、足し戻せないと言う**。速さが測れないのに 0 を足すのは、
> 「その間何も使っていない」と言うのと同じで、いちばん危ない読み方になる。

一晩の5件のうち、再現回数を測ったのは1件目だけで、**他の4件は未実測**。`confidence` を `検証中` に置いている理由。
5件目は**直ったあとの実物を読んで確かめた**（止める判定が `stale` より前にあり、`stale` は欄として残っている）。
**壊れていたときの再現は取っていない。**

**「先に書く」の型に、あとから2件が足された。**

- 2026-09-21 — 自分で次の回を予約していく定期実行が、あるとき「配る相手がいない」ので何も配らずに終わり、
  そこから3時間、記録が1行も増えなかった。外からは「**やることが無くて静か」と「切れて静か」が同じ見た目**で、
  受付役は**生きている定期実行を登録し直しかけた**（登録し直せば2本になり、どちらも自分が唯一だと思う）。
  直しとして、実行ごとの記録に「予約した次の時刻（しないなら理由）」と「配った件数（0なら理由）」を足し、
  読む側が4通り（古い形式の行／次を予約していない／次はまだ先／**予約した回が来ていない**）に言い分けるようにした
  （「やらなかった」は行に書けるが、「回が来なかった」は行に書けない。
  **マージするかは担当の判断に任せてあり、メインブランチに入ったかはここでは確かめていない**）
- 2026-09-27 — 「空振りのときも1行書く」監視役を新しく作ったら、その1行を書くツールが初回に許可を求めるため、
  **初回から約1時間、1行も載らなかった**（起動するはずだったのは3〜4回）。作った時刻を残し、起動するはずだった回数を数えるツールを足した
  （新しい定期実行は、生まれた瞬間から詰まっていることがあり、その状態だけは自分では書けない。
  **初回が許可待ちで止まった、は推測**）

### 外部の知見

**どちらも「分からない」を独立した状態として持たせる設計で、同じ結論に立っている**（2026-09-21 に確認）。

- **SQL の3値論理**（[modern-sql.com](https://modern-sql.com/concept/three-valued-logic)）—
  真と偽に加えて「unknown」を持つ。NULL は「**could be anything**」であって、
  **0 でも空文字でもない**。null 値が結果を左右するなら、結果は真でも偽でもなく unknown になる。
  **2値では足りないと判断して、言語の側に3つ目を置いた例**
- **監視の "No Data"**（[Grafana Alerting](https://grafana.com/docs/grafana/latest/alerting/guides/missing-data/)）—
  データが来ないことを**専用の状態**として扱い、どうするかを4通りから選ばせる
  （専用のアラートを出す／異常として扱う／正常として無視する／前の状態を保つ）。
  **「正常として無視する」は選択肢の1つとして明示されている**——
  つまり、**欠測を正常として扱うのは、知らないうちに起きることではなく、選んだ結果であるべきもの**

## 見直す条件

- **もっと広い原則（「独立していなければならない2つが重なると壊れる」）に足せる件が出たとき。**
  いまの5件は**どれも片方が「分からない／測っていない**」なので、広いほうはまだ根拠がない。
  重なりでも、監視する側と監視される側が重なる場合（証拠が**消える**）や、
  配分が自分の出力を食うループ（**暴走**する）は、**壊れ方の種類が違って誰かが気づく。**
  同じ原則にすると、この壊れ方のいちばんの特徴（**誰も気づかない**）が薄まる
- **3つ目の値の分岐を、読む側が書き忘れる事例が出たとき**。値で持つと、読む側が全部その分岐を書く。
  書き忘れた場所で気づかれないまま間違うなら、**値ではなくデータ型で持つ**形（分岐しないと取り出せない）に変える。
  **候補が1件ある**——消費をまとめて集める処理の台帳で「分からない」を値として正しく持っていたのに、
  数える側がその行を「覆えた」として数えた件。
  **見つけた側は別の原則として立てるべきだと判断している**ので、ここでは条件が満たされたとは数えていない。
  **2件目が出たら、この原則の側で引き取るかを決め直す**

## 原則

**目的から導ける結論を、結論のまま覚えない**。優先順位・順番・件数・名前のように後から変わる値は、記録の中で「導き方」と「いま導いた結果の例」に分けて書く。

書き込んでよいのは**判定の基準**であって、**当てはめた結果**ではない。

## なぜ

**物事は結びついて動く**。ひとつの前提が変われば、それに紐づく結論はすべて変わらなければならない。結論だけを書き写してあると、それらをすべて書き換える必要が出て、しかも**書き換え漏れのおそれ**が必ず残る。

結論を覚えた側は、前提が変わったことに気づけない。気づけないまま、古い結論を根拠に次の判断をする。これは古い事実が推論を狂わせるのと同じ事故で（→ [single-source-of-truth](single-source-of-truth.md)）、**優先順位のような「導ける結論」で起きると、被害が全体に及ぶ**。

もうひとつ。結果だけ書かれていると、**根拠ごと失われる**。「AとBが最優先」とだけ読んだAIは、なぜそうなのかを知らないまま順位を守る。新しいCが来ても、順位に入れられない。判定の基準が書いてあれば、変化に自分で追随できる。

## どう使う

- 覚えるのは**目的**だけ。「いま何が大事か」は毎回そこから導く。導いた結果は「今のところこれとこれ」という**例**として添え、固定の順位として書かない
- 何かを記録するとき、一度だけ問う。「**これは導けるか?**」導けるなら、導き方の方を書く
- その場で出た目安の数字を、規則として固定しない。実測値には**いつ測ったか**を添える。添えていない数字は、古くなったときに気づけない
- 変わったときに何を直す必要があるかを、書いた時点で分かるようにしておく

### 名前が変わるとき — 生データを書き換えずに済ませる

名前は、**実体を指すラベル**として扱う。ラベルが変わっても実体は同じものだと分かる、橋渡しの仕組みを持つ。

書いてあるものを3種類に分ける。

| 種類 | どこ | 名前が変わったら |
|---|---|---|
| **生データ** | `raw/`、会話ログ、コミット履歴、判断ログ | **触らない**。当時そう呼んでいた事実ごと残す |
| **加工済み** | `areas/`、`index.md`、各リポジトリの `CLAUDE.md` | **追随させる**。新しい名前に書き換える |
| **台帳** | `aliases.md`（リポジトリの直下） | **1行足す**。古い名前と新しい名前を橋渡しする |

手順は4つ。①`aliases.md` に1行足す（**これを先にやる**。後回しにすると忘れて、仕組みが知らないうちに壊れる） ②加工済みの側を書き換える ③生データは触らない ④`log.md` に1行残す。

探すときは逆から。**名前で引いて見つからなかったら `aliases.md` を見る**。この順序なら、生データを1バイトも書き換えずに、古い呼び名からも新しい呼び名からも引ける。

同じ解き方が外の世界で何度も選ばれている。共通しているのは**古い呼び名を消さないこと**。

| 分野 | やり方 |
|---|---|
| Web | 場所が変わっても古い URL を生かしたまま新しい URL へリダイレクトする |
| Wiki | ページ名を変えると、古い名前が自動でリダイレクトとして残る |
| データベース | 表示名とは別に変わらない内部の識別子を持ち、名前はその属性として付け替える |
| プログラム | 値を直接書かず、1箇所に置いて参照する |

名前を変えるコストが下がると、**変えてよくなる**。いい名前に付け替えられる状態そのものが利益。

### 未解決のまま抱えていること

逐語の生データと、後から変わる固有名詞は、そのままでは両立しない。台帳はその折り合いをつける仕組みだが、**どこまで台帳で吸収し、どこから書き換えるのが釣り合うのかは実測していない**。詳細は OPEN-QUESTIONS（キットには入っていない） の「逐語で残した記録と、後からの改名をどう両立させるか」。**答えが出ていないことを、答えが出たことにしない**のもこの原則の一部。

## 根拠

- 継続中 — 「目的と手段を入れ替えない」は作者の判断基準としても明示されている（→ 作者の判断基準の文書。キットには入っていない）

### 外部の知見

- [W3C Style Guide — Cool URIs don't change](https://www.w3.org/Provider/Style/URI)（2026-09-20 に開いて確認） — 「2年後、20年後、200年後にも通用する識別子を割り当てるのが務め」。日付・担当者名・技術の名前・状態を識別子に入れないよう戒めている。**変わりうるものを名前に埋めるな**という、ここでの原則とそのまま同じ考え方。リダイレクトの話は軽く触れる程度で、主眼は最初から変わらない名前を付けること
- Wiki のページ改名（改名すると古い名前がリダイレクトとして残る）、データベースのサロゲートキー（表示名とは別に持つ、変わらない内部の識別子） — いずれも「古い呼び名を消さずに橋を架ける」という同じやり方。**ただし出典には当たっていない**。一般によく知られたやり方という以上の裏付けは今のところ無い
- ソフトウェア設計でいうハードコーディングの回避と同じ構造。**定数を散らすほど、変更時に直し漏れる箇所が増える**。記録や指示文でも同じことが起きる
- エージェントのメモリに関する未解決問題としての memory staleness — メモリが古くなる経路のうち、「導けたはずのものを結論として保存した」ものは、事実の陳腐化より気づきにくい

## 見直す条件

- 導き直すコストが高すぎて、毎回同じ導出を繰り返しているなら、それは結論として固定してよい兆候。ただし**固定した日付と、見直す条件を添える**
- 前提が変わったのに古い結論が残っていた事故が起きたら、その値がどこから参照されていたかを洗い出す
- 台帳を引くのをAIが忘れて、古い名前を別物として扱った事故が起きたら、台帳の引き方（今は `AGENTS.md` 5 の運用頼み）を仕組みで支える形に変える
